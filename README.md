# WARNING in btrfs_create_pending_block_groups (fs/btrfs/block-group.c:2929, v7.4-rc2)

Syzkaller-found bug on Linux v7.4-rc2, reproduced and verified on the same
kernel build (fuzzing pipeline reproducer: confirmed=true, status=verified).

## Summary

A warning fired in the pending block group processing path during a
balance operation:

```
[  248.530541][T21682] BTRFS info (device loop5): balance: start -f -sstripes=0..7
[  248.535475][T21682] btrfs_abort_should_print_stack(__error)
[  248.535485][T21682] WARNING: fs/btrfs/block-group.c:2929 at btrfs_create_pending_block_groups+0x1044/0x1810, CPU#3: syz.5.22/21682
RIP: 0010:btrfs_create_pending_block_groups+0x1044/0x1810
```

The warning is generated by `btrfs_abort_transaction(trans, ret)` at
fs/btrfs/block-group.c:2929, which fired after `insert_block_group_item()`
returned an error during `btrfs_create_pending_block_groups()`. The
`btrfs_abort_transaction` macro (fs/btrfs/transaction.h) expands to a
`WARN_ON(btrfs_abort_should_print_stack(__error))` on first abort, which
is the WARNING seen here. The guest runs with `panic_on_warn=1`, which
escalates this warning to a kernel panic.

We have verified with `faddr2line` that
`btrfs_create_pending_block_groups+0x1044/0x1810` maps to
fs/btrfs/block-group.c:2929 in the v7.4-rc2 source, and that the kernel
tree matches the v7.4-rc2 tag with no local modifications to this file.
The bzImage sha256 is `e47d1c181af5f2615519de03ffc7bf73dad36b8ffb84b86e50391ed53bb731d6`
(see `environment.txt`).

## How to reproduce

Environment: Debian trixie x86_64 guest (6 GiB RAM, 4 vCPU, KVM), kernel
built from v7.4-rc2 with CONFIG_KASAN=y, CONFIG_BTRFS_FS=y, booted with
`oops=panic` and `panic_on_warn=1`. See `environment.txt` for the exact
QEMU command line and `kernel.config` for the configuration.

The crash depends on btrfs state built up by the preceding programs. The
reproducer is a multi-program syzkaller execution log (63 programs):

```sh
# in the guest, as root:
syz-execprog -procs=8 -threaded -repeat=0 -executor ./syz-executor repro.kernsight.prog
```

The programs are replayed repeatedly with 8 parallel workers (`-repeat=0`);
the execution order is not guaranteed to be strictly serial. The balance
operation that triggers the abort is visible in the console just before
the warning (`balance: start -f -sstripes=0..7`).

Verified by the fuzzing pipeline's reproducer machinery on a fresh VM
(reproducer pipeline outcome: confirmed=true, status=verified). A C
reproducer has not been included yet; it will be added once syzkaller's
C-repro stage passes for this bug.
